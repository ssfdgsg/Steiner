# Steiner 管理控制台重设计目标与前端实施计划

- 文档状态：设计与实施基线（阶段一至三已实现，见「实施进展」）
- 更新日期：2026-07-28
- 适用范围：`web/` React 管理控制台
- 目标读者：负责 Steiner Web 控制台设计与开发的前端 AI / 前端工程师
- 参考来源：七张控制台视觉参考图、当前仓库功能、现有 Admin API 与前端实现

## 1. 文档目的

本文定义 Steiner 管理控制台下一阶段重设计的产品目标、信息架构、视觉系统、页面结构、交互规则、数据边界、实施顺序和验收标准。参考图用于提取布局、信息密度、组件形态和运维工作流，不代表可以直接照搬其中的品牌、导航、示例模型、指标数值或不存在的后端能力。

前端实现必须以 `internal/server/server.go` 暴露的管理接口和 `web/src/api.ts` 中的类型为真实数据边界。参考图中存在但当前 API 未提供的数据，必须显示为明确的不可用状态、通过既有数据推导，或等待后端接口补齐；禁止用随机数、定时器或静态假数据伪装实时生产指标。

## 2. 产品定位

Steiner 是面向自建 GPU 推理集群的大模型 L7 网关与运维控制台，对外提供 OpenAI-compatible API，对内统一管理 vLLM、vLLM-Omni、SGLang 和 SGLang-Omni 等推理后端。

控制台服务于 LLM 平台工程师、MLOps 工程师、SRE、DevOps、GPU 集群运维人员和 AI 基础设施负责人。界面必须优先支持以下高频任务：

1. 判断网关、后端实例、请求队列和 PD 链路是否健康。
2. 识别延迟、容量、缓存命中率和实例异常的来源。
3. 查看、切换和编辑调度方案，并理解一次请求为何被路由到某个实例。
4. 注册、摘除、隔离或恢复推理后端。
5. 查看 KV Cache、容量队列、告警、扩缩容建议和集群成员状态。
6. 在执行高风险写操作前理解影响范围，并获得明确的操作反馈。

产品不是聊天应用、模型训练平台、营销网站或通用云资源门户。第一屏应直接呈现可操作的运行数据，不设置营销 Hero、功能介绍区或装饰性插画。

## 3. 总体设计目标

### 3.1 核心目标

- 建立统一、稳定、专业的数据密集型运维界面，减少当前页面之间的视觉和交互差异。
- 在 10 秒内让操作者判断“服务是否健康、哪里异常、是否需要操作”。
- 让关键状态、趋势、异常和推荐操作具备清晰的信息层级，而不是依赖大段说明文字。
- 同时支持总览监控与逐实例排障，避免用户在多个孤立页面间反复切换。
- 保留现有轻量技术路线、Hash Router、原生 `fetch`、`usePoll` 和 Go `go:embed` 部署模式。

### 3.2 设计原则

- **运维优先**：界面安静、克制、可扫描，强调状态与比较，不采用营销式构图。
- **表格优先**：实例、规则、告警、链路和日志等可比较数据以表格为主，卡片只用于 KPI、单项告警和明确的重复实体。
- **异常优先**：严重告警、不可用实例和容量风险优先出现在视线前部，但不能让正常状态被过度着色。
- **状态不只依赖颜色**：所有状态必须同时使用图标、文本、形状或标签表达。
- **数据可信**：区分实时值、轮询值、推导值、历史值和未接入值；显示最后更新时间与刷新状态。
- **渐进披露**：首层展示决策所需摘要，详情通过抽屉、展开行、标签页或二级页面呈现。
- **危险操作可恢复**：摘除、隔离、删除、应用策略和执行扩缩容必须经过确认，并说明影响范围。

## 4. 参考图统一结论

七张参考图共同定义了以下设计方向：

- 深色企业级基础设施控制台，主色为冷青蓝，成功、警告、严重和信息状态使用绿、琥珀、红、蓝四色语义。
- 固定左侧主导航，主内容区采用 12 列响应式网格；页面标题、上下文控制和刷新工具位于内容区顶部。
- KPI 卡片用于总请求、活跃实例、平均延迟、缓存命中率、GPU 利用率和队列深度等核心指标。
- 折线图承担时序趋势，柱状图承担模型或实例分布，仪表/环形图只承担有限的单值占用率展示。
- 数据表格具有固定表头、状态标签、排序、筛选、分页和行级操作；选中实例通过右侧详情抽屉查看。
- 调度解释器采用“查询条件 + 决策流程 + 决策依据 + 结构化明细”的可解释布局。
- KV Cache 和队列页面强调缓存统计、模型分布、后端明细与请求处理阶段。
- 告警与扩缩容页面强调当前风险、推荐实例数、容量趋势和历史执行记录。
- 总览页将 KPI、吞吐趋势、实例分布、调度规则和最近告警组合为一屏工作台。

参考图之间存在两种导航形态：顶部全局导航加多级侧栏，以及单层窄侧栏。Steiner 当前功能规模不需要双重全局导航，最终采用单一固定侧栏，避免重复入口和有效内容宽度损失。页面内的集群、模型、时间范围和刷新频率属于上下文工具栏，不进入全局导航。

## 5. 信息架构与路由

必须继续使用 Hash Router，确保嵌入式静态托管在刷新时不依赖服务端 rewrite。

### 5.1 一级导航

1. **总览** `#/overview`
2. **调度方案** `#/presets`
3. **后端实例** `#/backends`
4. **调度解释器** `#/explain`
5. **运行监控** `#/runtime`
6. **KV Cache 与队列** `#/cache-queue`
7. **告警与扩缩容** `#/operations`

保留原始指标入口，但将其置于侧栏底部“外部工具”区域，以外链图标标识，并在新标签页打开 `/metrics`。默认路由由当前调度方案页调整为 `#/overview`。旧 Hash 路由必须保留兼容，不得造成已有书签失效。

### 5.2 导航规则

- 桌面端侧栏宽度建议为 224px，可折叠至 64px；折叠态只显示图标，并提供 Tooltip。
- 当前路由采用左侧 3px 主色指示条、轻量背景和高对比文本，不使用大面积发光。
- Logo、产品名和环境标识置于侧栏顶部；版本、系统状态、最后同步时间置于底部。
- 页面标题不得重复产品名，例如使用“告警与扩缩容”，不使用“Steiner - 告警与扩缩容建议”。
- 侧栏项目使用 Lucide 图标；存在图标库时禁止手绘 SVG。

## 6. 全局应用框架

### 6.1 顶部上下文栏

主内容区顶部保持 56px 高度，包含：

- 当前页面标题与可选面包屑。
- 集群/环境选择器；单集群时显示只读环境标识，不制造无效下拉框。
- 系统健康摘要，以绿色/琥珀/红色状态点和文字表达。
- 最后更新时间、自动刷新开关、刷新频率选择和立即刷新图标按钮。
- 主题切换、帮助和用户入口仅在真实能力存在时显示。

全局刷新默认沿用 `usePoll`。页面失焦时暂停高频轮询，重新获得焦点后立即刷新；请求进行中不得启动重叠轮询。用户手动刷新时保留现有内容并显示局部刷新状态，不应让整页闪烁。

### 6.2 内容区

- 最大内容宽度不设窄屏上限，运维表格应充分利用宽屏；左右内边距桌面端 24px，大屏 32px。
- 页面区块以无外框布局或独立数据面板呈现，不在卡片内继续嵌套卡片。
- 面板圆角不超过 8px，边框比背景略亮；阴影仅用于抽屉、弹窗和浮层。
- 典型纵向顺序为：页面工具栏、异常摘要、KPI、主趋势、详情表格。

## 7. 页面详细需求

### 7.1 总览 `#/overview`

**目标**：提供跨调度、实例、性能、缓存和告警的一屏健康摘要，作为默认工作台。

**页面结构**：

1. 顶部四个 KPI：总请求数、活跃实例、平均延迟、缓存命中率。
2. 左侧 7/12 宽“实时吞吐量”时序图，右侧 5/12 宽“实例分布”柱状图。
3. 左侧“调度规则表”，右侧“最近告警”。
4. 小屏下按 KPI、吞吐、告警、实例分布、规则表的业务优先级纵向排列。

**KPI 规则**：

- 主值使用 28-32px 半粗体，单位使用较小字号并与值基线对齐。
- 趋势值只在存在可比时间窗口时显示；当前 API 无历史对比时显示“暂无对比数据”，不得伪造“较昨日”。
- 迷你趋势线只在存在真实历史序列时显示。
- 活跃实例可由 `BackendView.healthy && !cordoned && !ejected` 推导，总实例取列表长度。
- 缓存命中率可按可用后端快照汇总，但必须在 Tooltip 中说明聚合口径；无法可靠加权时显示实例中位数并明确口径。

**图表和列表**：

- 吞吐图优先展示网关 RPS；当前接口未提供历史序列时显示结构化空状态，并提供 `/metrics` 入口。
- 实例分布按模型或引擎分组。只有真实标签中存在模型信息时才按模型展示，否则改为按引擎展示。
- 调度规则表展示策略名、类型/预设、目标策略槽位、优先级（若有）、状态和更新时间（若有）。缺失字段不生成假值。
- 最近告警最多展示 3-5 条，按严重级别和发生时间排序，支持“查看全部”进入告警页。

### 7.2 调度方案 `#/presets`

**目标**：展示当前生效方案、关键运行结果、可用预设与策略表达式，并支持安全切换和编辑。

**页面结构**：

1. 当前方案摘要：方案名称、生效策略槽位、状态、简短说明和“切换方案”主操作。
2. 可用数据存在时展示平均延迟、缓存命中率、吞吐量和 GPU/KV 使用率 KPI；否则直接进入方案内容，不保留空 KPI 占位。
3. 预设方案采用紧凑选择列表或分段列表，不使用大面积营销卡片。
4. 当前方案详情展示 filter、score 表达式、适用场景和风险提示。
5. 高级策略编辑器采用 Grafana 风格双模式：`可视化构建` 与 `表达式`。可视化模式生成健康、负载、KV、缓存等常用 filter 条件和线性 score 代价因子；表达式模式保留完整 Expr DSL。
6. score 的语义是代价，分数越小越优；构建器正系数表示惩罚、负系数表示奖励。编辑内容通过 `POST /admin/policies/validate` 只读编译校验后，才允许调用现有热更新接口。
7. 含括号、函数、动态 map 或混合逻辑的复杂表达式不强行反向解析；自动保留在表达式模式，并提示用户使用均衡模板重建。

**交互要求**：

- 应用方案前显示确认弹窗，列出目标策略槽位、当前方案、目标方案和影响说明。
- 应用中禁用重复提交；成功后刷新 presets 状态并 Toast 提示；失败保留用户上下文和表达式。
- 自定义表达式必须使用等宽字体，支持基础语法高亮、行号或至少清晰的错误定位。
- 不在前端自行解释或执行表达式；服务端结果是唯一权威。

### 7.3 后端实例 `#/backends`

**目标**：快速比较所有推理实例的健康、负载、队列、缓存和吞吐，并完成注册、隔离、恢复与移除。

**主表字段**：

- 实例 ID
- 状态
- 引擎
- 地址
- 权重
- Inflight
- Running / Waiting
- KV 使用率
- 缓存命中率
- 生成吞吐
- 最近快照时间
- 操作

**页面结构与交互**：

- 表格上方提供文本搜索、状态筛选、引擎筛选和“注册实例”按钮。
- 默认将异常、隔离和已摘除实例置于更高关注级别，但不擅自改变后端返回顺序；通过显式排序控件实现。
- 点击行打开右侧详情抽屉，不触发行级操作。抽屉宽度建议 420-480px。
- 详情抽屉包含基础信息、标签、Prometheus 变量、GPU/KV 指标、请求负载、错误信息和最近更新时间。
- `cordon`、`uncordon` 和删除操作使用图标加文本菜单。删除必须二次确认并显示实例 ID 与 URL。
- “隔离中”“已摘除”“不健康”“活跃”必须有明确状态标签。`healthy`、`cordoned`、`ejected` 的组合应映射为单一主状态，同时在详情中保留原始标志。
- 注册实例使用表单弹窗，按后端 API 实际字段校验；提交失败不得关闭弹窗。

### 7.4 调度解释器 `#/explain`

**目标**：回答“给定模型、Prompt、策略和会话时，请求为什么被路由到该实例”，帮助排查缓存亲和、过滤和评分问题。

**页面结构**：

- 左侧 320-360px 查询面板：模型、Prompt、策略槽位、Session ID、执行按钮与最近查询历史。
- 右侧主区域：决策摘要、路由流程、决策依据和逐后端评分表。
- 窄屏下查询面板置于主内容上方，历史记录折叠。

**决策展示**：

1. 入站请求参数。
2. Session/策略上下文。
3. 候选后端可用性与 filter 结果。
4. Prefix match、inflight、running、waiting、KV usage 等评分输入。
5. score 排名与最终选中实例。

当前 `ExplainResp` 只提供最终路由、策略、策略槽位和逐后端评分，不提供完整服务端执行步骤。因此流程图必须基于实际响应构造为“输入 -> 候选过滤 -> 评分排序 -> 最终路由”的可信流程，禁止虚构服务端内部阶段或耗时。

评分表需展示 Backend、Available、Filter Pass、Score、Prefix Match、Inflight、Running、Waiting、KV Usage 和 Error。选中后端高亮但不隐藏未通过候选项；失败原因直接显示在对应行。

### 7.5 运行监控 `#/runtime`

**目标**：集中观察集群请求、实例健康、PD 分离链路和服务运行状态。

**页面结构**：

1. 请求总量、活跃后端、平均延迟、队列深度 KPI。
2. 全宽吞吐/延迟趋势图，支持时间范围和粒度选择；历史指标未接入时展示接入提示而非假图。
3. PD 分离组表：策略、策略槽位、Prefill 实例、Decode 实例、链路数量和健康摘要。
4. 展开 PD 组后显示 Link 的 Prefill、Decode、带宽和 Inflight。
5. 集群成员表：成员 ID、地址、Leader 状态和本机标识。

运行监控只展示观测与诊断，不混入实例注册或策略编辑。全屏按钮仅作用于主趋势面板；退出全屏必须支持 `Esc`。

### 7.6 KV Cache 与队列 `#/cache-queue`

**目标**：观察 KV Prefix Cache 的总体规模、缓存效率和容量队列压力，定位具体模型或后端瓶颈。

**页面结构**：

1. KV Cache KPI：启用状态、占用字节、节点数，以及可用时的命中率。
2. 按模型缓存使用分布；只有后端或指标接口提供模型维度时显示。
3. 后端缓存详情表：实例、KV usage、hit rate、prefix 相关信息和快照状态。
4. 队列 KPI：启用状态、当前深度、最大深度、最大等待时间。
5. 按模型队列分布表或条形图，数据来自 `QueueResp.by_model`。
6. 请求处理阶段只在存在 Pending/Running/Completed 对应真实数据时展示；当前接口不提供 Completed，不得生成该数值。

进度条必须显示数值和阈值，宽度固定，避免动态内容造成布局位移。超过 80% 使用警告色，超过 90% 使用严重色；若后端提供不同阈值，应以后端配置为准。

### 7.7 告警与扩缩容 `#/operations`

**目标**：将当前告警、容量状态、扩缩容建议和操作历史聚合成明确的运维决策页面。

**页面结构**：

1. “活跃告警”按 Critical、Warning、Info 排序，默认使用紧凑列表或三列告警摘要；超过三条后进入表格视图。
2. “集群活跃状态”展示实例使用情况和 GPU/CPU/内存/网络指标；仅展示当前数据源实际提供的指标。
3. “自动扩缩容建议”展示模型、当前实例数、建议实例数、方向和原因。
4. “容量趋势”展示实际使用、当前容量、推荐容量以及扩缩容事件标记；需要历史接口支持。
5. “扩缩容日志”展示时间、方向、变更数量、原因、关联策略和结果；需要后端历史接口支持。

**重要能力边界**：

- 当前 `GET /admin/alerts` 可以支持活跃告警。
- 当前 `GET /admin/autoscale` 可以支持扩缩容建议。
- 当前接口没有执行扩缩容、容量时序和扩缩容历史能力。因此第一阶段只提供建议查看，不显示可点击的“执行扩容”按钮。
- 后续若增加执行接口，操作必须显示当前与目标副本数、影响模型、建议原因和不可逆风险，并要求二次确认。操作状态需要服务端任务 ID 支持，不能以一次 HTTP 成功等同于扩容完成。

- `--text-muted`: `#718096`
- `--accent`: `#21B8E6`
- `--accent-strong`: `#168FD1`
- `--success`: `#2CCB8C`
- `--warning`: `#F0A629`
- `--danger`: `#F05B66`
- `--info`: `#4CA7F5`

所有文本与背景必须满足 WCAG 2.1 AA。弱化文字不低于 4.5:1；大字号和非文本图形不低于 3:1。图表网格线保持低对比，数据线必须明显高于网格线。

### 8.2 排版

- 字体优先使用系统无衬线栈，中文环境包含 `PingFang SC`、`Microsoft YaHei`。
- 页面标题 24px/32px，面板标题 16px/24px，正文 14px/22px，辅助文字 12px/18px。
- KPI 主值 28-32px，表格与紧凑控件 13-14px。
- 数字启用 tabular numbers，表达式、实例 ID、URL 和时间使用等宽字体。
- Letter spacing 固定为 0，不使用负字距，也不随视口宽度缩放字号。

### 8.3 间距与尺寸

- 基础间距单位 4px；常用间距为 8、12、16、20、24、32px。
- 控件高度：紧凑 32px，默认 36px，主操作 40px。
- 图标按钮固定为 32x32px 或 36x36px，避免 Hover 或加载状态改变尺寸。
- KPI 卡片最小高度 124px；图表区建议高度 280-340px；表格行高 44-48px。
- 面板圆角 6-8px，输入框和按钮圆角 4-6px，状态 Badge 圆角 4px。

### 8.4 图标与状态

- 使用现有依赖中的图标库；如新增，优先选择 `lucide-react` 并评估包体积。
- 图标按钮必须包含 `aria-label` 和 Tooltip。
- Critical/错误：圆形感叹号或三角警示图标 + 红色文本标签。
- Warning：警示图标 + 琥珀标签。
- Success：圆点/勾选图标 + 绿色文字。
- Info：信息图标 + 蓝色文字。
- Disabled/未知：中性灰标签，不与健康状态混淆。

## 9. 核心组件规范

应从现有 `web/src/components.tsx` 演进共享组件，避免各页面重复实现。

- `AppShell`：侧栏、顶部上下文栏、内容区和移动端导航。
- `PageHeader`：标题、辅助状态和页面级操作。
- `MetricCard`：标题、主值、单位、趋势、迷你趋势和 Tooltip；所有区域可选。
- `StatusBadge`：统一语义状态映射，支持图标与文本。
- `DataPanel`：标题、工具区、内容与状态容器；禁止嵌套 `DataPanel`。
- `DataTable`：排序、空状态、加载、行选择、分页和横向滚动。
- `FilterBar`：搜索、筛选、时间范围、刷新工具；移动端允许换行。
- `UsageBar`：值、阈值、颜色与可访问标签。
- `ChartPanel`：标题、图例、时间范围、图表、空状态和错误状态。
- `DetailDrawer`：实例与规则详情，支持键盘关闭和焦点恢复。
- `ConfirmDialog`：危险操作确认，焦点锁定，明确主次按钮。
- `EmptyState`、`ErrorState`、`Skeleton`、`InlineNotice`：统一异步状态。
- `ToastRegion`：写操作结果，不替代需要用户处理的页面级错误。

图表实现优先复用轻量、可审计且支持 Canvas/SVG 的成熟库。如果继续坚持零图表依赖，则仅实现需求明确、交互简单的原生 SVG 折线/柱状图，并为数据点提供可访问的文本摘要；不得手写完整通用图表引擎。新增依赖前应更新技术决策记录。

## 10. 数据、状态与 API 映射

| 页面 | 当前可用接口 | 当前可实现范围 |
|---|---|---|
| 总览 | `/admin/backends`、`/admin/presets`、`/admin/alerts`、`/admin/queue` | 活跃实例、快照聚合、当前策略、最近告警、当前队列 |
| 调度方案 | `/admin/presets`、`/admin/presets/{name}/apply`、`/admin/policies/{name}` | 预设、应用方案、编辑策略 |
| 后端实例 | `/admin/backends` 及其注册/删除/cordon 接口 | 实例列表、详情、注册、隔离、恢复、移除 |
| 调度解释器 | `/admin/explain` | 候选过滤、评分与最终路由解释 |
| 运行监控 | `/admin/pd`、`/admin/cluster`、`/admin/queue`、`/admin/backends` | 当前 PD 链路、成员、队列和实例快照 |
| KV Cache 与队列 | `/admin/kvcache`、`/admin/queue`、`/admin/backends` | Cache 总量、节点、当前队列和后端快照 |
| 告警与扩缩容 | `/admin/alerts`、`/admin/autoscale` | 活跃告警与只读扩缩容建议 |

### 10.1 缺失能力清单

下列参考图能力需要后端或指标历史接口支持，前端不得自行伪造：

- 任意 24 小时/7 天历史时序和“较昨日”对比。
- 网关总请求数、RPS、P50/P95/P99 延迟的管理 API 聚合结果。
- GPU、CPU、内存、网络的集群级历史利用率。
- 模型到实例的权威映射（除非 labels 已提供）。
- 告警历史、扩缩容历史和容量事件。
- 执行扩缩容及异步任务进度。
- Completed 请求数量和完整请求流水线统计。
- 用户、权限、区域和多集群管理。

缺失能力的 UI 策略按优先级为：隐藏非核心区块；展示带接入说明的空状态；链接到 `/metrics` 或既有监控系统。禁止显示看似真实但无数据源的零值。

### 10.2 异步状态

- 初次加载使用局部 Skeleton，保留页面框架，避免全屏 Spinner。
- 轮询刷新保留旧数据，并在更新时间附近显示刷新中状态。
- API 错误使用页面内错误条，显示可理解的中文信息、HTTP 状态和重试按钮。
- 单个面板失败不能阻塞其他独立面板。
- 空数据必须区分“功能未启用”“当前无数据”“筛选无结果”和“接口异常”。
- 数据超过两个刷新周期未更新时显示“数据可能已过期”。

## 11. 交互与可访问性

- 所有交互元素支持键盘操作，焦点样式清晰，Tab 顺序与视觉顺序一致。
- 弹窗和抽屉打开后锁定焦点，关闭后焦点回到触发元素；支持 `Esc` 关闭非危险确认层。
- 表格行本身可点击时，行内按钮必须阻止冒泡，并提供独立可访问名称。
- Tooltip 不能承载完成任务所必需的信息；移动端无法 Hover 时仍可获得核心含义。
- 图表必须同时提供图例、单位、时间范围和文本摘要，不能仅靠颜色区分序列。
- 自动刷新不得打断输入、关闭菜单、重置筛选、跳转分页或使焦点丢失。
- 写操作使用乐观更新要非常谨慎；实例隔离、删除和策略应用以服务端确认后更新为准。
- 时间统一显示本地时间并在 Tooltip 中提供完整 ISO 时间；同一页面不得混用时区。

## 12. 响应式策略

该产品以桌面运维为主，优先适配 1366px、1440px、1920px 和更宽屏幕，同时保证 1024px 可用。

- `>= 1440px`：完整侧栏，12 列网格，KPI 四列，主图双列。
- `1024-1439px`：侧栏可折叠，KPI 两列或四列紧凑模式，图表按 7/5 或单列布局。
- `768-1023px`：默认折叠侧栏，KPI 两列，详情抽屉占视口 60%-70%。
- `< 768px`：侧栏变为覆盖式导航，KPI 单列或两列，数据表横向滚动，抽屉全屏。

不得为移动端删除高风险操作的确认步骤。表格不强行转为大量嵌套卡片；保持横向滚动、冻结关键列或提供精简列视图。

## 13. 技术实现边界

- 保持 React 18、TypeScript、Vite 5 和 Hash Router。
- 保持原生 `fetch` 和当前 `ApiError` 语义，优先扩展 `usePoll` 而不是引入全局状态库。
- 保持 CSS Variables 和内网无 CDN 依赖；任何字体、图标或图表依赖必须打包到构建产物。
- 不删除现有路由，不改变 Admin API 请求语义，不在前端复制后端调度逻辑。
- 组件和页面使用明确的 TypeScript 类型，不用 `any` 绕过接口差异。
- 构建产物继续输出到 `internal/webui/dist/` 并由 `go:embed` 嵌入。
- 前端变更完成后执行 `make web`，提交对应 dist；再执行项目现有完整测试和构建。

## 14. 建议实施阶段

### 阶段一：设计系统和应用框架

### 阶段二：重构现有四个功能页

- 调度方案、后端实例、调度解释器、运行态迁移到新应用框架。

- 优先补齐实例详情抽屉、统一筛选和统一错误状态。

### 阶段三：新增聚合页面

- 新增总览、KV Cache 与队列、告警与扩缩容页面。

- 轮询不重叠、不重置用户输入，并显示最后更新时间。

- 状态不只依赖颜色，文本对比度满足 WCAG 2.1 AA。
- 弹窗和抽屉焦点管理正确，自动刷新不造成焦点丢失。

- 受影响模块现有测试通过；新增关键状态映射和交互测试。
- 完整项目测试套件通过。

## 16. 实施进展

阶段一至三已落地，代码位于 `web/src`，后端补充位于 `internal/metrics` 与 `internal/server`。

已实现：

- 设计系统与应用框架：`web/src/styles.css` 语义 token、`web/src/App.tsx` 固定侧栏 + 上下文栏、七个 Hash 路由（旧路由保留兼容）。
- 公共组件：`web/src/components.tsx`（`Panel`、`MetricCard`、`DataTable`、`Drawer`、`ConfirmDialog`、`Async`、状态徽标）、`web/src/charts.tsx`（内联 SVG 折线/柱状/迷你趋势）、`web/src/icons.tsx`。
- 轮询治理：`web/src/hooks.ts` 的 `usePoll` 页面隐藏时暂停、请求不叠加、保留旧数据并暴露最后更新时间；顶栏统一控制频率与手动刷新。
- 七个页面全部使用真实接口数据；缺失能力显示带说明的空态或提示条。

后端补充的三个只读端点（第 10.1 节缺失能力的第一批闭环）：

- `GET /admin/stats`：`metrics.Aggregate()` 从自身 Registry 汇总累计请求量、错误率、时延与 TTFT 分布（直方图桶插值）、按模型与后端拆分，叠加后端池汇总与排队即时深度。
- `GET /admin/stats/history?minutes=`：`metrics.History` 环形缓冲（15s × 1440 ≈ 6 小时，进程内、重启清空），差分得到瞬时 RPS、错误率、区间平均时延，并由 `RuntimeProbe` 同点采集队列深度、可用实例数、KV 规模与命中率。
- `GET /admin/models`：模型路由拓扑与池内健康计数，提供「模型 → 实例」的权威映射。

仍未闭环（保持第 10.1 节结论，前端不伪造）：

- 主机级 GPU / CPU / 内存 / 网络利用率（不在网关采集范围）。
- 告警历史、扩缩容执行与历史记录（副本变更由订阅 webhook 的外部控制器落地）。
- 跨实例聚合与超过缓冲容量的长周期时序（以 Prometheus 为事实来源）。

## 17. 非目标

本轮重设计不包含：

- 新增模型训练、模型文件管理、批处理任务或在线推理 Playground。
- 构建完整 IAM、RBAC、审计日志或多租户计费系统。
- 用前端假数据补齐后端尚未实现的历史监控能力。
- 将控制台改造成通用 Kubernetes 管理平台。
- 为追求视觉效果引入 3D、插画、复杂动效或重型 UI 框架。

最终实现应让 Steiner 看起来和使用起来都像一个可信的推理基础设施控制面：状态清楚、数据可追溯、操作有边界、异常可定位，而不是只有深色主题和图表外观的静态 Dashboard。
